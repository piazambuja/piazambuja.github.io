# Job application

Goal: help the user spend applications where they have a real chance, and send applications that are accurate. Works for any field; base every judgment on the user's own CV and profile.

## Hard rules

- **Never invent facts.** Any question whose answer depends on the user (language level, salary expectation, notice period, visa or work authorisation, whether they use the company's product, years with a tool, phone number) is asked, not guessed. Write open answers only from what the CV, profile or user said.
- **Never submit without an explicit ok** for that specific application. An application usually can't be edited after it's sent.
- Answers must be true even when a "yes" would score better. If the user hasn't used the product, say so honestly and write about what they know of it publicly.
- Don't create accounts, solve captchas or type passwords for the user.

## Step 1: get the inputs

- The posting: a link (read it) or the pasted text. If the page doesn't load fully, scroll or ask for the text.
- The user's current CV and profile. If they were just updated, use the new versions.
- Anything not in the CV that the posting will ask about: target salary, language levels, availability, work model and contract preferences.

## Step 2: fit evaluation (fixed format)

1. **The role in one line:** title, company, seniority, location / remote, employment type, salary if shown, and how many applicants if visible.
2. **What matches:** requirements the user meets, each tied to concrete evidence from their CV ("asks for 3+ years of X: you have 8").
3. **Gaps:** requirements the user doesn't meet or meets only partly. Separate must-haves from nice-to-haves.
4. **Risks:** what is most likely to stop the process. Common ones: a required language level above the user's; a different tool or platform ecosystem; a role that is a step down or a different job family (e.g. people management vs. individual contributor); a contract model the user may not want; on-site requirements.
5. **Rough fit** (e.g. strong / partial ~50% / weak) and a **recommendation**: apply, apply with caveats, or skip, with the reason in two sentences. When skipping, suggest what to look for at the same company instead, if it's a good employer for the user.

When the user sends several postings, rank them by fit.

## Step 3: filling in the application

- Open the form and list every field and page before filling, so you can ask all the user-dependent questions in one message instead of one per page.
- Attach the user's current CV, never an old file stored on the site. Check which file is selected.
- **Flag divergent data before using it:** a phone or email that the site pre-filled differently from the CV, a language level in the CV that is lower than the posting requires. Ask which one is right.
- Open questions ("Why do you want to work here?", "Describe a relevant project"): tie 2–3 real facts from the user's experience to what the posting describes. Write in the language of the posting. Keep it short and specific, no flattery. Show the text to the user.
- Mandatory consent checkboxes (privacy, data processing) can be accepted when the user has asked to apply; mention that you did.
- External sites may block automation (captcha, bot checks, account creation). Say so as soon as it happens, leave the page open for the user to clear it, and continue after.

## Step 4: before submitting

Show a summary of everything that will be sent: CV file, contact data, each answer (short open answers in full) and any choice you made on the user's behalf. Then ask "Can I submit?". After submitting, confirm that the site shows the application as sent.

## End of every turn

If an application is left unfinished, end with a pending checklist per application: where it stopped (e.g. "page 6 of 12"), what's already filled, and exactly what the user needs to answer or do to continue.
